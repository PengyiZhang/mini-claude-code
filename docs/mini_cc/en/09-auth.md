# 09 — Authentication, Authorization & Tenant Isolation

> The HTTP routing layer splits "who you are" (tenant), "what you can do"
> (scope), and "can you come in right now" (rate limit) into three
> orthogonal gates, all backed by a single JSON file (`keys.json`). This
> chapter covers the `mini_cc/auth/` API key registry, the scope grammar,
> the Bearer validation pipeline, the shared-secret fallback for inbound
> workflow webhooks (`_service_for_unauth`), and how `tenant_id`
> propagates down into the 3-tier plugin/storage namespace. Tool-level
> authorization is a separate axis — see chapter 06.

---

## Problem & motivation

mini_cc is a multi-tenant agent backend: several `tenant_id`s share one
process, one filesystem, one Anthropic API quota. Without an explicit
tenant boundary, four failures show up immediately:

1. **Tenant A uses tenant B's project.** The `/tenants/{tid}/projects/{pid}/...`
   path has `tid` declared by the tenant in the URL and `pid` being the
   target project. If routes trust the URL `tid` without verifying it
   matches the tenant bound to the API key, tenant A can forge `tid=B`
   and read B's sessions.
2. **Read-only key runs writes.** You hand CI a `read:*` key to pull
   metrics, but if the routing layer doesn't distinguish read/write,
   that key can POST `/send` and burn LLM quota. You need coarse
   per-method (GET vs non-GET) scope gating.
3. **Expired/revoked keys keep working.** Ops rotates a leaked key, but
   the old one is still in CI env vars. The registry must support lazy
   expiry, instant revoke, and grace-period rotation, and the validation
   path must consult disk (or the registry cache) on every request —
   never a startup snapshot.
4. **External webhooks can't get in.** GitHub, Stripe, SendGrid POST into
   your service and they won't carry your Bearer token. If webhook routes
   also enforced Bearer + tenant match, every inbound integration would
   break. You need a "no Bearer, but shared secret" bypass.

`mini_cc/auth/` solves the first three; `_service_for_unauth` in
`mini_cc/server/routes/workflow_v2.py` solves the fourth. Authorization
(tool-level) lives separately in `mini_cc/core/permissions.py` and
`permissions.toml` — see chapter 06. This chapter is transport-layer only.

## Design & implementation

### 1. `KeyRecord`: a key's complete identity

Each entry in the registry is a `KeyRecord` (`mini_cc/auth/keys.py:52-72`):

```python
@dataclass
class KeyRecord:
    key: str                     # "mck_<32 hex>"
    tenant_id: str               # which tenant this key belongs to
    scopes: list[str]            # ["*"] / ["sessions:write", "files:read"] ...
    created_at: str              # ISO8601
    expires_at: str | None       # None = never expires
    label: str                   # human-readable, e.g. "ci-readonly"
    rotated_from: str | None     # if produced by rotate(), the original key
```

`is_expired` (`keys.py:63-69`) is lazy: expired records stay in `keys.json`
(so `list_for` can show history) but are rejected at `lookup` time. Note
the fail-open tradeoff: a malformed/unparseable `expires_at` is treated
as **not expired** (`keys.py:67-68`, comment "malformed → not expired
(fail-open)") — a permissive choice that keeps keys working through a
clock/format glitch rather than locking everyone out.

The key format `mck_<32 hex>` (`keys.py:30-31`, `_KEY_HEX_BYTES = 16` →
32 hex chars) is generated by `secrets.token_hex` (`keys.py:104`): 128 bits
of cryptographic randomness, unguessable, unenumerable.

### 2. `TenantKeyRegistry`: thread-safe JSON backend

The whole registry is one `keys.json` file, structured as
`{api_key: KeyRecord_dict}` (`keys.py:86-117`). Every write goes through
`threading.Lock` + atomic rename (`_write` at `keys.py:267-285`:
`tmp = path.with_suffix(...+".tmp")`, `json.dump`, then
`os.replace(tmp, path)`). `os.replace` is atomic on the same filesystem,
so cross-process reads see either the old file or the new file — never a
half-written JSON.

Seven public methods map one-to-one to every CLI and admin action:

| Method | Line | Purpose |
|---|---|---|
| `generate(tenant_id, scopes, expires_in, label)` | `keys.py:97` | New key |
| `lookup(key)` | `keys.py:119` | Called by validation, **filters expired** |
| `list_for(tenant_id)` | `keys.py:136` | Admin listing (includes expired) |
| `revoke(key)` | `keys.py:147` | Immediate delete |
| `rotate(key, grace_hours, ...)` | `keys.py:157` | Rotate, optional grace |
| `update(key, scopes, expires_in, label)` | `keys.py:205` | Incremental patch |

The key design in `rotate` (`keys.py:187-203`): with `grace_hours > 0`, the
old key is rewritten as a new record expiring at `now + grace_hours`,
rather than deleted. That way CI can use either key during the rotation
window without breaking on a deploy-order race. `grace_hours=0` (the
default) is a hard revoke — the old key dies instantly.

Backward compat: `_record_from_raw` (`keys.py:236-255`) tolerates the v0
bare-string shape (old `keys.json` was just `{"mck_xxx": "tenantA"}`),
auto-promoting to `KeyRecord(scopes=["*"], label="migrated")`, and the
file isn't normalized on disk until the next mutation — old fixtures stay
byte-identical and tests don't break on the format upgrade.

### 3. The scope grammar: one string, three wildcards

A scope is a colon-joined `resource:verb` (`mini_cc/auth/scope.py:1-15`).
Semantics live in `scope_allows(held, required, method)` (`scope.py:56-111`):

| Held | Matches |
|---|---|
| `*` | anything |
| `read:*` | any GET |
| `write:*` | any non-GET |
| `sessions:*` | any method on `/sessions/...` |
| `sessions:read` | GET on `/sessions/...` |
| `sessions` | shorthand for `sessions:*` |

`read` ≡ `GET`, `write` ≡ everything else (`_verb_for_method` at
`scope.py:52-53`). This mapping is fixed at the HTTP layer, so route
declarations don't need to specify the verb —
`Depends(require_scope("sessions:write"))` resolves against the actual
request method.

Wildcard resolution has three cases (`scope.py:85-110`):
- **Verb-prefixed wildcard** (`read:*` / `write:*`): the left side is a
  verb, not a resource; matches by method.
- **Resource-scoped** (`sessions:*` / `sessions:write`): the left side is
  a resource; matches the route's `required` resource.
- **Full-wildcard resource** (`*:read`): supported for symmetry, rare.

### 4. The Bearer validation pipeline: `_resolve`

`mini_cc/server/deps.py:73-95` is the core. Every protected endpoint hangs
a `Depends(require_scope("xxx"))` off it, which runs this chain internally:

```
GET /tenants/A/projects/p1/sessions/s1  Authorization: Bearer mck_yyy
   │
   ▼
_parse_bearer(authorization)              deps.py:35-41
   │  split "Bearer" + token; bad format → None
   ▼
key missing? → 401 Unauthorized "missing bearer token"      deps.py:76-77
   │
   ▼
reg.lookup(key)                           deps.py:79
   │  consults keys.json + lazy expiry
   ▼
rec is None? → 401 "unknown or expired api key"            deps.py:80-81
   │
   ▼
rec.tenant_id != tid? → 403 Forbidden "does not match tenant"  deps.py:82-83
   │  ← this is the tenant boundary: A's key hitting B's URL dies here
   ▼
scope_allows(rec.scopes, required, method)?                deps.py:84
   │  no → 403 "insufficient_scope", with WWW-Authenticate header + held/required detail
   ▼
request.state.tenant_id = tid; return tid                  deps.py:94-95
```

Three things matter:
- **Tenant match comes before scope** (`deps.py:82` precedes `:84`). Order
  matters: first confirm the key belongs to this tenant, then ask what it
  can do. Otherwise a `*`-scoped key from tenant B would pass the scope
  check and only get caught later, with a muddier error.
- **401 vs 403 distinction.** 401 = "I don't know who you are" (missing /
  unknown / expired key); 403 = "I know who you are, but you can't do
  that" (tenant mismatch / insufficient scope). Clients can distinguish
  "should re-auth" from "should request more access."
- **`insufficient_scope` carries a `WWW-Authenticate` header** (`deps.py:90-91`),
  following the RFC 6750 OAuth2 Bearer error format — standard OAuth2
  clients parse it automatically.

`require_tenant` (`deps.py:44-53`) is a backward-compat shim equivalent to
`require_scope("*")`, kept for routes that haven't migrated. New code
always declares its resource explicitly via `require_scope`.

### 5. Consumption on the route side: each endpoint declares its scope

Taking the sessions router as example (`mini_cc/server/routes/sessions.py`):

```python
# sessions.py:35
def create_session(..., tid: str = Depends(require_scope("sessions:write"))):
# sessions.py:61
def get_session(..., tid: str = Depends(require_scope("sessions:read"))):
# sessions.py:161 — /send consumes both a scope token and a rate-limit token
def send(..., tid: str = Depends(check_rate_limit_scope("sessions:write"))):
```

`check_rate_limit_scope("sessions:write")` (`deps.py:131-140`) is a composite
dependency: it runs `require_scope` first, then `_apply_rate_limit`, raising
429 + `Retry-After` on denial (`deps.py:143-156`). The per-tenant token
bucket is keyed on the resolved `tid`, so one tenant's runaway CI can't
starve another.

Admin routes use `admin:read` / `admin:write` (`routes/admin.py:39, 46, 63, ...`)
and `_check_key_belongs_to` (`admin.py:32-35`) re-checks that the target
key belongs to the current tenant — **admin is not a superuser**, it can
only manage its own tenant's keys. An `admin:write` key from tenant A
cannot rotate tenant B's key; it gets a 404 (deliberately not leaking
existence).

### 6. `_service_for_unauth`: the shared-secret bypass for external webhooks

GitHub / Stripe / SendGrid POST inbound and they can't carry a Bearer. The
workflow V2 inbound webhook route deliberately **does not** go through
`require_scope`:

```python
# mini_cc/server/routes/workflow_v2.py:401-437
@runs_router.post("/{run_id}/webhook/{step_id}", response_model=RunOut)
def resolve_webhook_wait(run_id, step_id, body=None, webhook_id=None,
                          pid=..., pm=Depends(get_pm)):
    validate_id(pid)
    svc = _service_for_unauth(pm, pid)        # ← no Bearer check, no tenant check
    run = svc.get_run(pid, run_id)
    ...
    step = next((s for s in d.steps if s.id == step_id), None)
    expected_wh = step.config.get("webhook_id")
    if expected_wh:
        if not webhook_id or webhook_id != expected_wh:
            raise Unauthorized("invalid or missing webhook_id")  # shared-secret gate
    ...
```

`_service_for_unauth` (`workflow_v2.py:440-459`) is just `_service_for`
with the tenant check removed — the docstring says it plainly: "The
shared-secret (webhook_id query param) gate replaces the tenant boundary
for this specific endpoint."

**Security model**: the gate here is the `webhook_id` in step config — a
random string embedded in the GitHub webhook URL as
`...?webhook_id=<secret>`. To forge a webhook, an attacker must know
`run_id`, `step_id`, *and* this `webhook_id` — all three. For external
integrations this is the standard pattern (Slack's signing secret,
Stripe's webhook token work the same way). If a step doesn't configure
`webhook_id`, this endpoint is fully open — that's the step author's
explicit choice; the framework doesn't force it.

The W4 inbound email route (`workflow_v2.py:467-493`) goes through the
same `_service_for_unauth`; the gate is provided by `step_id` plus the
mail filters in step config.

### 7. `tenant_id` propagation into storage & plugin namespaces

After auth resolves `tid`, it doesn't just sit on `request.state` — it
flows through the ProjectManager all the way into storage paths.
`mini_cc/plugins/paths.py` defines three tiers:

```
tier_dir(data_dir, PluginTier.SYSTEM)                     # global shared
tier_dir(data_dir, PluginTier.TENANT, tenant_id=tid)      # per-tenant isolation
tier_dir(workspace, PluginTier.PROJECT)                   # per-project isolation
```

`project_tier_dirs(data_dir, tenant_id, workspace)` (`paths.py:71-79`)
returns these three as an ordered list; discovery walks system → tenant →
project, and same-named entries in later tiers override earlier ones
(`paths.py:19-20`, comment: "project > tenant > system").

So one tenant's `.mini_cc/skills/`, `.mini_cc/memory/`, `.mini_cc/mcp.json`
are a physically separated directory tree from another tenant's. Even if
a routing bug slips past tenant validation, discovery only looks inside
the wrong tenant's directory — no cross-tenant contamination. This is
defense in depth: auth is the first gate, filesystem layout is the second.
Full details of 3-tier MCP plugin discovery are in chapter 11; we don't
expand here.

The storage layer (`mini_cc/storage/fs.py`) is similarly organized under
`<data_dir>/tenants/<tid>/projects/<pid>/`, and the ProjectManager caches
assembled projects keyed by `(tenant_id, project_id)` (`projects/manager.py:142`).
`tenant_id` lands in project meta (`manager.py:114`), and workspace
resolution + tier directory assembly both build on it.

## Operation & verification

### CLI: keygen / list / rotate / revoke

```bash
# 1. Create a full-permission key for tenant "acme"
python -m mini_cc.server keygen acme
# → mck_3f9a...  tenant=acme  scopes=*  expires=never

# 2. Create a read-only, 7-day CI key
python -m mini_cc.server keygen acme --scopes "read:*" --expires-in 7d --label "ci-readonly"
# → mck_...  tenant=acme  scopes=read:*  expires=2026-07-06T... [ci-readonly]

# 3. List all keys for acme (including expired)
python -m mini_cc.server keys list acme

# 4. Rotate with a 24-hour grace window — old key keeps working inside the window
python -m mini_cc.server keys rotate mck_<old> --grace-hours 24
# → new: mck_<new>  (rotated from mck_<old>…)
#   old: mck_<old>  expires=<now+24h>

# 5. Immediate revoke
python -m mini_cc.server keys revoke mck_<leaked>
# → revoked
```

CLI code is at `mini_cc/server/cli.py:152-208`; `_format_record`
(`cli.py:143-149`) renders that human-readable one-liner. The `keygen`
subcommand is registered at `cli.py:302-313`.

### HTTP: verifying the three gates with curl

```bash
# A. Missing Bearer → 401
curl -s -o /dev/null -w "%{http_code}\n" \
  http://127.0.0.1:8002/tenants/acme/projects/p1/sessions
# → 401

# B. Unknown key → 401
curl -s -o /dev/null -w "%{http_code}\n" -H "Authorization: Bearer mck_deadbeef" \
  http://127.0.0.1:8002/tenants/acme/projects/p1/sessions
# → 401  (unknown or expired api key)

# C. Tenant mismatch → 403
#    Use acme's key against another tenant's URL
curl -s -o /dev/null -w "%{http_code}\n" -H "Authorization: Bearer $ACME_KEY" \
  http://127.0.0.1:8002/tenants/other/projects/p1/sessions
# → 403  (api key does not match tenant)

# D. Insufficient scope → 403 + insufficient_scope
#    Use a read:* key to POST
curl -i -X POST -H "Authorization: Bearer $READONLY_KEY" \
  -H "Content-Type: application/json" \
  -d '{"user_input":"hi"}' \
  http://127.0.0.1:8002/tenants/acme/projects/p1/sessions/s1/send
# HTTP/1.1 403 Forbidden
# WWW-Authenticate: Bearer scope="sessions:write"
# {"error":{"code":"forbidden","message":"key lacks required scope: sessions:write",
#           "details":{"code":"insufficient_scope","required":"sessions:write",
#                       "held":["read:*"]}}}

# E. Expired key → 401 (even with scope *)
python -m mini_cc.server keygen acme --expires-in 1s   # expires in 1 second
sleep 2
curl -s -o /dev/null -w "%{http_code}\n" -H "Authorization: Bearer $(that key)" \
  http://127.0.0.1:8002/tenants/acme/projects/p1/sessions
# → 401

# F. Admin route: a normal * key → 403 (missing admin scope)
curl -s -o /dev/null -w "%{http_code}\n" -H "Authorization: Bearer $ACME_KEY" \
  http://127.0.0.1:8002/tenants/acme/admin/keys
# → 403

# G. Shared-secret webhook: no Bearer, correct webhook_id → 200
curl -X POST \
  "http://127.0.0.1:8002/tenants/acme/projects/p1/workflow_v2/runs/r1/webhook/step1?webhook_id=$SECRET" \
  -H "Content-Type: application/json" -d '{"event":"push"}'
# → 200 (assuming run r1's step1 is webhook_wait with webhook_id=$SECRET)

# H. Shared-secret webhook: wrong webhook_id → 401
curl -s -o /dev/null -w "%{http_code}\n" -X POST \
  "http://127.0.0.1:8002/tenants/acme/projects/p1/workflow_v2/runs/r1/webhook/step1?webhook_id=wrong" \
  -d '{}'
# → 401  (invalid or missing webhook_id)
```

### Playwright: the web UI login flow

The web frontend (`mini_cc/web/`) treats the API key as the user's "login"
credential: an input collects the key, the frontend stores it in
`localStorage`, and every fetch carries `Authorization: Bearer <key>`. The
tenant field comes from a form and must match the key's bound tenant, or
the backend returns 403. Manual verification:

```bash
cd mini_cc/web && npm run dev
# Open the browser, enter an acme key with tenant="acme" → land on the main page
# Deliberately type tenant="other" → 403 toast "api key does not match tenant"
```

## Pitfalls & best practices

1. **Editing `keys.json` doesn't take effect — actually it does.** The
   `TenantKeyRegistry` keeps no in-memory cache — every `lookup` does a
   full `json.load` under the lock (`keys.py:127-128`). So edits apply
   immediately, no restart needed. But **don't write it with a text
   editor**: concurrent requests will race your write with route reads
   and you may serve a half-written file. Always go through the CLI or
   admin routes, which use atomic `os.replace` rename.
2. **`*` scope is not admin.** A `*` key can call every business endpoint,
   but admin routes require `admin:read` / `admin:write` (`admin.py:39, 46`).
   `scope_allows` matches resources strictly, and `*` wildcard matches any
   resource *including* `admin` — so `*` actually **can** manage admin.
   If you want "all business perms but no key management," use an explicit
   list like `sessions:* files:* projects:*`, not `*`. This is a known
   scope footgun.
3. **Forgot to update CI after rotate.** `grace_hours` gives you a window,
   but the default is 0 (hard revoke, `keys.py:200-203`). Production
   rotates must pass `--grace-hours 24` (or longer), or CI goes red the
   instant you swap the key.
4. **`expires_at` parse failure fails open.** `is_expired` returns False
   for a malformed `expires_at` (`keys.py:67-68`). This is deliberate
   (avoids a clock/format glitch locking out every key), but it means if
   you hand-write `keys.json` and typo the date, that key effectively
   never expires. Generate keys via CLI / admin API; don't hand-write.
5. **The webhook endpoint has no tenant boundary.** `_service_for_unauth`
   (`workflow_v2.py:440`) deliberately skips the tenant check. Your
   `webhook_id` must be unguessable (at least 128 bits), or an attacker
   can brute-force it. The `webhook_id` in step config is the only gate —
   don't use predictable values like `run_id`, `step_id`, or `github`.
6. **`TenantPrincipal` is a compat alias.** `keys.py:75-84` keeps it for
   old imports. New code should always use `KeyRecord`, which carries
   scopes / expires_at; `TenantPrincipal` only has key + tenant_id.
7. **Multi-worker deployment.** `threading.Lock` only protects within one
   process (`keys.py:92`). Under multiple workers (gunicorn -w 4),
   cross-process safety relies on the atomic `os.replace` rename. But
   **concurrent writes overwrite each other**: worker A writes, worker B
   writes from a stale snapshot, clobbering A. If you run multi-worker
   with frequent key operations, consider an external registry (Redis) or
   funnel key management into a single-process sidecar. Most deployments
   do key ops rarely enough that this doesn't bite.

## Summary

mini_cc's auth/authz is a combination of three orthogonal gates:

- **`TenantKeyRegistry`** (`mini_cc/auth/keys.py`): JSON-backed key store
  with lazy expiry, atomic writes, grace-period rotation, and backward
  compat with the v0 format.
- **`scope_allows`** (`mini_cc/auth/scope.py`): a single string grammar
  expressing coarse-to-fine permissions via `resource:verb` plus three
  wildcard tiers.
- **`require_scope` / `_resolve`** (`mini_cc/server/deps.py`): a FastAPI
  dependency that chains Bearer parsing → registry lookup → tenant match
  → scope check → rate limit, using the right 401/403/429 code at each
  failure.

The bypass is workflow V2's `_service_for_unauth` (`workflow_v2.py:440`),
which swaps the tenant boundary for a shared secret in step config, so
external webhooks can get in. `tenant_id` propagates via the ProjectManager
into the three tier directories (system/tenant/project) and into storage
paths; even if the routing layer misses, the filesystem layout is the
second line of defense.

Tool-level authorization (interactive permission prompts, deny-list hooks)
is a separate axis — see chapter 06. Three-tier MCP plugin discovery is
detailed in chapter 11.
